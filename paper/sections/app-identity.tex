\section{Bit identity}
\label{sec:identity}

Claim C1 was that a feed and a seed give the same report bytes on every
target the application builds. The test cases were the golden feed plus
\R{id/frozen/wasm32-under-node/cases} generated cases. They vary the
generator, the history length and start, the holiday calendar, the
horizon, the number of paths and the seed. Any differing byte falsifies
the claim.

\paragraph{The tested matrix.}
\begin{itemize}
\item \textbf{On one arm64 Mac:} native code in debug and release builds;
  the UniFFI binding used by the iOS application, exercised from Rust; and
  WebAssembly under Node. The golden feed alone was also checked through
  the desktop application's IPC path, the web application's tests and the
  Swift package.
\item \textbf{On x86\_64}, a GitHub Actions workflow on a Linux runner
  checks native code (debug and release) and WebAssembly. It covered only
  the golden feed, at commit \texttt{26ed672} before the fix, and passed.
  It now also covers the generated cases. \TODO{Result of the extended
  x86\_64 workflow run on the fixed engine, to be filled in after the
  push.}
\item \textbf{Not tested:} a physical phone, JavaScriptCore on a device,
  and other compiler versions.
\end{itemize}

\paragraph{Outcome.} For the frozen engine, the claim is falsified.
WebAssembly reproduced every feed but only
\R{id/frozen/wasm32-under-node/reports_identical} of
\R{id/frozen/wasm32-under-node/cases} reports: one value differed by one
unit in the last place. The cause was a dependency feature that sent part
of the sampler's math to the platform's library natively and to a
pure-Rust library in WebAssembly (Appendix~\ref{app:identity}). After a
post-freeze fix, all \R{id/post/wasm32-under-node/cases} cases agree on
the tested matrix on the Mac (Table~\ref{tab:identity}), and the shipped
golden files did not change. The frozen results were not regenerated. V0
and V2 rerun with the fixed engine on \R{d/pf-accounts} development
accounts (\R{d/pf-forecasts} forecasts) are byte-identical to the frozen
ones, but that is a sample, not a proof that no held-out number would
move.

\subsection{Cause and fix}
\label{app:identity}
In case \R{d/c1-case} of the generated set, one quantile on forecast day
\R{d/c1-day} was \texttt{\R{d/c1-native}} natively and
\texttt{\R{d/c1-wasm}} in WebAssembly.

\paragraph{The cause.} The engine samples with the \texttt{rand\_distr}
crate \citep{rand_distr_crate}. The design document said that crate's
default build uses the pure-Rust \texttt{libm} \citep{libm_crate}, so its
math would be identical on every platform. That was wrong from the day the
dependency was added:
\begin{itemize}
\item No crate enables the feature documented to switch to platform
  math, \texttt{std\_math}.
\item But the crate's default \texttt{std} feature links the standard
  library. Its concrete \texttt{f64} normal and exponential samplers call
  \texttt{exp} and \texttt{ln} as methods, which Rust resolves to the
  standard library's inherent methods ahead of the \texttt{libm}-backed
  trait.
\item Natively on macOS that is the system math library; in WebAssembly
  it is Rust's port of \texttt{libm}. On this machine the two disagree on
  about \R{d/c1-ln-share}\% of inputs to \texttt{ln} and
  \R{d/c1-exp-share}\% to \texttt{exp} (\R{d/c1-draws} million random
  inputs).
\item The samplers reach those functions only in the tail and wedge
  branches of the ziggurat method \citep{marsaglia2000ziggurat}, so few
  reports were affected.
\item The realistic generator also called the standard library's
  \texttt{ln} and \texttt{exp} directly.
\end{itemize}

\paragraph{The fix.} After the freeze, \texttt{rand\_distr} was built
without default features, which leaves only its \texttt{libm} path, and the
generator was changed to call \texttt{libm}. The fix changed one native
report, case \R{d/c1-case}, to exactly the value WebAssembly had always
produced. The evaluation code's closed-form Gaussian CRPS still uses the
standard library's \texttt{exp}. That affects scoring only, never a
forecast.
