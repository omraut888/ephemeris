Technical Specification — v1.0

EPHEMERIS

A personal financial trajectory engine — iOS, Android, Web, and Desktop from one shared core — that doesn't show you where your money has been, but computes, with honest uncertainty, where it's actually headed. Built on the same mathematics used for spacecraft navigation and quant risk pricing, pointed at the one thing everyone instantly understands: their own money.

Platforms: iOS · Android · Web · Desktop
Shared core: Rust
Domain: FinTech + Real-Time Systems
Companion: emergent research paper (Phase 6)

00 Positioning Statement

An ephemeris is the table astronomers and spacecraft navigators use to predict exactly where a body will be at a future time, computed by fusing noisy observations into a precise trajectory estimate with quantified uncertainty. EPHEMERIS does the same thing for personal finances: your real financial state isn't your raw account balance — it's a hidden quantity corrupted by noisy, delayed signals (pending transactions, subscription timing drift, irregular income) — and the app continuously estimates that true state and projects it forward as a probability cone, not a single number.

Why this is the right "universal" project

Nobody needs domain background to get the pitch — "an app that forecasts where your money is actually headed, like a weather forecast, with honest odds instead of a fake-precise number" is instantly graspable to anyone. The sophistication lives entirely in the engine (state estimation, stochastic simulation, real-time sync); the surface is as universal as a bank balance.

01 System Architecture

Bank/Txn Data (Plaid sandbox) ──▶ On-Device Categorization (CoreML / equiv.) │ ▼ Kalman Filter — True State Estimation │ ▼ Monte Carlo Trajectory Simulation ──▶ probability cone, N future paths │ ▼ CRDT Sync Layer ──▶ iOS · Android · Web · Desktop, live & offline-consistent

The entire estimation/forecasting engine is written once, in Rust, then compiled to native mobile bindings, WASM for the web client, and a native desktop build via Tauri — one engine, three shells, rather than three independent reimplementations. This single decision is the strongest systems-maturity signal in the whole project.

02 Core Engine — Kalman Filter State Estimation core

Raw transaction data is noisy and delayed — a pending charge, a subscription that renews on a drifting date, a paycheck that lands a day early or late. A Kalman filter treats your "true" financial state as a hidden variable and continuously fuses noisy observations into a best estimate with a quantified confidence interval, exactly the technique used for spacecraft position estimation and sensor fusion in autonomous vehicles.

Predict: x̂ₖ⁻ = A x̂ₖ₋₁ + B uₖ Pₖ⁻ = A Pₖ₋₁ Aᵀ + Q Update: Kₖ = Pₖ⁻ Hᵀ (H Pₖ⁻ Hᵀ + R)⁻¹ x̂ₖ = x̂ₖ⁻ + Kₖ (zₖ − H x̂ₖ⁻) Pₖ = (I − Kₖ H) Pₖ⁻ x̂ₖ = estimated true financial state at time k zₖ = noisy observation (raw transaction/balance data) Pₖ = estimate uncertainty (covariance)

State variables include: true disposable balance (net of known pending obligations), estimated recurring-expense baseline, and income regularity variance — each with its own uncertainty, not a single blended number.

Monte Carlo Trajectory Forecasting core

From the Kalman-filtered state and its estimated variance in spending behavior, simulate thousands of plausible future paths rather than projecting a single deterministic line — identical in spirit to how quant desks price risk via simulated outcome distributions. The output is a probability cone: "70% of simulated futures show you can afford this by March" rather than a false-precision single number.

03 On-Device ML Categorization core

A lightweight on-device model (CoreML on iOS, an equivalent lightweight model on Android) categorizes transactions locally — the app functions fully offline, and raw financial data never needs to leave the device unless the user explicitly opts into cloud sync. This is a genuine privacy-engineering decision, not a feature-list bullet point.

04 Offline-First Real-Time Sync via CRDTs core

Financial state must stay live and consistent across phone, web, and desktop even through offline edits and reconnects — the same class of problem Figma and Linear solve with Conflict-free Replicated Data Types. Each device holds a local CRDT-backed state; merges are mathematically guaranteed to converge without a central lock, so editing a budget offline on the phone and later opening the desktop app never produces a conflict dialog.

05 Interface Direction

The core visual metaphor should be literal, not decorative: your financial future rendered as an actual trajectory cone — mission-control aesthetic, dark-mode-first, precise typography — closer to Linear, Arc, or Raycast than to a typical budgeting app. The goal is that a non-technical person immediately understands the cone ("the shaded area is how sure the app is"), while the visual language itself signals the engineering rigor underneath before a single line of copy is read.

07 Build Phases

Phase 1
Core engine. Kalman filter + Monte Carlo simulation in Rust, validated against Plaid sandbox data, CLI-only to start. Get the math right before touching any UI.
Phase 2
Web shell. Compile the core to WASM, build the React front end with the trajectory-cone visualization. Fastest path to something demoable.
Phase 3
Mobile shells. iOS first (Swift + UniFFI + CoreML categorization), then Android. Reuse the same core — this phase is mostly binding and UI work, not new engine logic.
Phase 4
Desktop + sync. Tauri desktop build, CRDT sync layer wired across all shells so edits propagate live and merge cleanly offline.
Phase 5
Polish pass. Interface refinement toward the mission-control aesthetic — this is the phase that makes the difference between "working app" and "the kind of thing people screenshot."
Phase 6
emergent, not planned upfront
Once the engine is producing real forecast cones against real/sandbox data, the natural next question appears on its own: does the 70% confidence cone actually contain the real outcome 70% of the time? Most forecasting tools never check their own calibration. That question becomes the paper — see below.

08 The Companion Paper — How It Actually Emerges

"Does State-Estimation-Based Forecasting Improve Calibration Over Standard Budgeting Heuristics? An Empirical Comparison" — once EPHEMERIS is producing real probability cones, the honest empirical question is whether those cones are actually trustworthy, not just visually compelling. Compare EPHEMERIS's Kalman-filter-plus-Monte-Carlo forecasts against standard baselines (moving average, naive linear projection — the logic most budgeting apps already use) on two axes: raw forecast error, and — the genuinely underexplored part — calibration, whether a stated 70% confidence interval actually contains the true outcome roughly 70% of the time across many forecasts. This reuses data and output you already have from building the app; it isn't a second project, it's the natural question the first one raises.

Why this ordering matters for the story

This is deliberately Phase 6, not Phase 0. You can't meaningfully ask "are my uncertainty bounds calibrated" until you have a working engine producing real bounds to test — which means the paper genuinely emerges from the build, not the other way around. That's both the more defensible research posture and the more honest interview story.

09 Defending It In An Interview

The question you will get

"Isn't this just a budgeting app with fancy math on top?" Answer with the calibration result, not the feature list: most forecasting tools — including ones built by well-funded companies — never check whether their confidence intervals are honest. You built the engine, then empirically tested whether its uncertainty estimates actually mean what they claim to mean, and have a real answer either way. That's the difference between a feature and a finding.
